## BUG-2026-001 · 小米 9 所有弹窗看不见（v0.9.32 修复）

- **现象**：素材箱点「收进档案」无弹窗；桌面端与荣耀 50 正常。仅小米 9 复现。
- **根因**：小米 9 系统 WebView 停在 **Chrome 83**（MIUI 不随系统更新 WebView）。弹窗遮罩用 `inset:0`（Chrome 87+ 才支持），旧内核解析不了 → `position:fixed` 元素没有任何偏移量，被摆到文档流末尾（视口外 top:886px，视口仅 808px）。**弹窗有 DOM 但在屏幕外**。uiautomator 报 0 边界是 WebView 无障碍树未刷新的假象，别被骗。
- **修复**：style.css 9 处 `inset:0` → 显式 `top/right/bottom/left:0`；3 处 `aspect-ratio`（Chrome 88+）加 `@supports not` 固定高度兜底；app.js 加 flex gap 垫片（仅 Chrome<84 生效）。
- **教训**：CSS 新属性（inset、aspect-ratio、:has、dvh）在安卓 WebView 上都是兼容性雷；写 fixed 定位一律用显式四边偏移。

## BUG-2026-002 · 录音转文字 403（v0.9.33 修复）

- **现象**：AI 助手/素材箱录音转文字报 `HTTP 403：API Key 不对或用不了`。
- **根因**：「语音转文字」槽位绑了硅基流动配置但**没绑模型**，代码兜底拿配置的聊天默认模型（`tencent/Hunyuan-MT-7B`，翻译模型）去打 `/audio/transcriptions` → 上游 403 "Illegal operation"。Key 与免费额度本身正常。
- **修复**：手机端 ai_slots.asr 直填 `FunAudioLLM/SenseVoiceSmall`（当场恢复）；安卓 Ai.java 与桌面 server.js 均去掉聊天默认模型兜底，改为明确提示去设置绑定。
- **教训**：兜底逻辑不能跨用途——聊天模型的默认值拿去打语音接口必然 403；槽位绑定要「配置+模型」成对校验。

## BUG-2026-003 · XingChenASR 模型 403（v0.9.34 修复）

- **现象**：转文字下拉选 `XingChenAGI/XingChenASR-V3.2-Ultra` 转写报 403。
- **根因**：该系列是硅基流动上架的付费模型，免费 Key 调用即 403；模型列表直接来自上游 /models，不区分免费/付费。

- **教训**：上游模型列表会含付费项，按用途展示模型时要过滤到「该 Key 实际可用」的子集。

## BUG-2026-004 · AI 图入库 NOT NULL（v0.9.29 主端 / v0.9.34 静态站修复）

- **现象**：AI 生成图片「存进档案/收进档案」全部失败，报 `NOT NULL constraint failed: photos.taken_year`。
- **根因**：photos 表 `taken_year/place/event` 三列 NOT NULL，而多处 AI 图入库给 taken_year 传 null。
- **修复**：主端 v0.9.29 统一传 0；**静态站同类雷 3 处**（chat.js 图入库、db.js 备份导入 `p.taken_year || null`、db.js addPhoto 无兜底）在 v0.9.34 排掉。
- **教训**：NOT NULL 列的 INSERT 调用点要全项目 grep 收齐逐个核对，`x || null` 的写法在 x=0 时也会变 null。

## BUG-2026-007 · 手机导出 PDF 失败 / Word 找不到文件（v0.9.35 修复）

- **现象**：导出 PDF 失败；Word 成功后「打开看看」点不开；手机存储里找不到文件。
- **根因**：① 安卓 LocalServer 的 `/api/export/pdf` 明确报缺（需桌面 Chrome 引擎）；② Word/PPT 落在 app 私有目录 `files/users/<uid>/files/exports/`，浏览器点 `/files/*.docx` 无处理程序，文件管理器也看不到。

## BUG-2026-009 · 每次打开 APP 都要重新登录（v0.9.36 修复）

- **现象**：安卓端每次冷启动都回到登录页，账号密码要重输一遍。
- **根因**：`LocalServer.start()` 用 `new ServerSocket(0, ...)` 让系统随机分配端口，每次启动 origin 都不同（`http://127.0.0.1:<随机>`）。`localStorage` 是按 origin 隔离的 —— 上次登录写下的 `mylife.token` 下次读不到，`boot()` 里 `!API.auth.token()` 直接踢回登录页。跟 token 有效期、WebView 缓存都无关。
- **修复**：
  - `LocalServer` 固定端口 `34567`（被占用时才退回随机）。
  - 兜底：原生 `NativeIO.getToken/setToken`（SharedPreferences）存一份，`api.js` 的 `token()` 读不到 localStorage 就从这里取，`setToken()` 双写。
  - 登录页加「记住我」（默认勾选）；不勾只写 `sessionStorage`，关 APP 即失效。
  - token 有效期 30 天 → 180 天。
- **验证**：`cat /proc/net/tcp6 | grep 8707`（34567 的十六进制）确认端口已固定。

## BUG-2026-011 · 改章名什么都不写，章名被清空（v0.9.37 修复）

- **现象**：目录点「改章名」，弹窗里提示“什么也不写就保留原名”，直接点确定后章名变空白。
- **根因**（两处同时存在，缺一不可）：
  1. 点击处理里用 `document.querySelector('[data-ch-title="id"]')` 取当前章名，但**渲染时从未输出过 `data-ch-title` 属性** → 取到的永远是空串，弹窗连默认值都没有；
  2. `DB.updateChapter(chid, v, '')` 对空串照写不误，第三个参数还把 `summary` 一起覆盖成空。
- **修复**：目录行 / 整本阅读 / 章节页标题三处补 `data-ch-title`；新增 `chTitleCache` 回填（不依赖 DOM 是否可见）；空值或纯空格＝不改名并提示「没写名字，章名还是「XXX」」；`DB.updateChapter` 自己加边界（title 空跳过、summary 未传不动）；历史空章名兜底显示「第 N 章」；待归档页隐藏「改章名」。
- **教训**：写「留空＝保留原值」的交互，必须先保证默认值真的能取到；DOM 里没有的 data 属性不会因为代码里写了 querySelector 就存在。

## BUG-2026-016 · 素材箱录音「收进档案」后声音找不到（v0.9.38 修复）

- **现象**：素材箱里录一段 → 转成文字 → 「收进档案」→ 档案里只有文字，录音在哪儿都翻不到（素材箱待归档列表里也消失了）。
- **根因**：`adoptQuick()` 只建了一条 `kind='text'` 的条目，**音频没有跟着进档案**；素材被标 `adopted` 后从 `status='open'` 的待归档列表里消失，音频只剩 `quick_notes.media_path` 这个没有任何界面读取的字段。文件其实一直在 `data/users/<id>/files/audio/` 里，**不是被删了**。
- **修复**：
  1. 收进档案时走 `attachQuickAudio()`：登记进 `media`（`kind='audio'`）并挂到条目上（条目 `kind='media'`），档案页 / 待归档直接可回放。**复用同一份文件不复制**，登记后清空素材的 `media_path` = 文件所有权移交，之后删素材不会误删条目在用的录音。
  2. `repairQuickAudio()`：开机跑一次、幂等，把历史上「只搬了文字」的录音素材补挂回对应条目（条目已删的跳过，音频原地不动）。
  3. `listOrphanAudio()` / `attachAudioFile()`：扫 `files/audio/` 减去 media、素材、访谈分段已在用的，剩下的就是「找不到的那些」；素材箱底部「🔍 还有 N 段录音没挂进档案」可试听、可放进档案。
  4. 「最近收进档案的」加 🎙️/📷 标记与「去看看」，点了直接跳那一章；顺带修掉照片收录后素材原图不删的空间泄漏。
- **教训**：收录（adopt）这种「搬东西」的函数，必须把**媒体本体**和**文字**一起搬；只搬文字等于在界面上把文件藏起来。凡是"打标记让它从列表消失"的操作，都要先确认目标位置真的能看到它。

## BUG-2026-017 · 装到手机上还叫「我的人生档案」（v0.9.40 修复）

- **现象**：登录页、网页标题、关于页都已是「岁月记录助手」，但安卓装完后桌面图标、应用列表、系统「设置 → 应用管理」里仍显示旧名「我的人生档案」；给用户指路「设置 → 应用 → 岁月记录助手 → 权限」时他根本找不到这个应用。
- **根因**：改名那轮只改了 `web/` 里的显示文案，**漏了安卓原生资源**：
  1. `android/app/src/main/res/values/strings.xml` 的 `app_name` 仍是旧名——`AndroidManifest.xml` 的 `android:label="@string/app_name"` 就是靠它，桌面名/应用列表/系统设置全走这一处；
  2. `res/layout/activity_main.xml` 启动页 TextView `android:text` 写死旧名；
  3. `MainActivity.java` 两处录音权限安抚提示（「到系统设置 → 应用 → 我的人生档案 → 权限」）也是旧名，属**引导用户去一个不存在的应用名里点**。
- **修复**：三处统一改「岁月记录助手」；同时把打包链路的产品名收进常量：
  - `tools/build-exe.js` 新增 `APP_NAME` / `EXE_FILE`，产物改为 `岁月记录助手-v<版>-windows.exe` / `-android.apk`，工作目录程序 `dist/win/岁月记录助手.exe`，使用说明与 `最新版本在这里.txt` 同步；旧包归档正则同时认 `MyLife-` 与 `岁月记录助手-` 前缀（否则改名后旧包归档失效）。
  - `tools/make-release.py` / `tools/make-backup.py` 的文件名、说明标题、zip 内条目统一新名。
- **验证**：`aapt2 dump badging` → `application-label:'岁月记录助手'`；手机装好后系统「应用信息」显示「岁月记录助手 版本 0.9.40」；桌面图标名已是「岁月记录…」（小米桌面 6 字截断，长按可见全名）。
- **教训**：改名是**跨端清单活**，不是搜一遍 `web/` 就完事。凡是「用户在系统里看到的字」，至少四处要对齐：安卓 `strings.xml` 的 `app_name`、启动页布局、原生代码里的提示文案、打包脚本的产物名。改名后必须 `aapt2 dump badging` 验一遍 label，光看网页不算验完。

## BUG-2026-018 · 素材全选导出，App 直接闪退（v0.9.41 修复）

- **现象**：素材箱「选择 / 导出素材」→ 全选 30 条（171MB）→ 按钮变「正在打包…」→ **App 进程消失**，Download 里一个文件都没有。用户以为"没反应"，其实是 OOM 被杀（`dumpsys meminfo` 之后报 `No process found`）。
- **根因**：`DB.exportMaterials()` 一次性把所有素材的 base64 读进内存（171MB 字符串，UTF-16 约 342MB），再 `JSON.stringify(pack)` 复制一份整包 → 峰值 600MB+。小米9（6GB，largeHeap）也扛不住。
- **修**：
  1. `MainActivity.java` 新增 `NativeIO.exportBegin/exportAppend/exportEnd/exportAbort`：一次 `openOutputStream` 保持流打开，允许分段 write。
  2. `DB.exportMaterialsStream(ids, onItem)` 逐条读、逐条序列化，把单条 JSON 文本交出去；内存峰值降到单条素材。
  3. `inbox.js` 拼 `{"format":...,"items":[` + 每条 JSON（逗号分隔）+ `]}`，写进同一个文件。
  4. 老 APK 无新接口时退回 `exportMaterialsByVolume()`（16MB 分卷、多文件），也不会崩。
- **验证**：小米9 实机全选 30 条导出成功，文件 171MB，无闪退（改前必崩）。
- **教训**：任何「把 N 个文件读进内存再拼一个大字符串」的导出，都要按**逐条流式**来做；桌面浏览器能过的写法，手机上就是闪退。判据：数据量 > 50MB 就必须流式。

## BUG-2026-019 · 条目操作按钮压成竖排单字、且淡到看不见（v0.9.41 修复）

- **现象**：手机上正文条目下方那排按钮（□ ↑ ↓ 换章 润 改 ＋图 传 退 删）挤成一坨，`换章`「＋图」竖着排成两行，整排透明度 35%，老人家根本看不出这里有按钮。
- **根因**：`.en-acts{display:flex;gap:14px;opacity:.35}` 三个问题叠一起 ——(1) 9 个按钮 + 9×14px 间距 = 389px，超出 361px 容器，`nowrap` 下每个被压到 24px，中文逐字换行；(2) `opacity:.35` 靠 `.en:hover` 提亮，**触屏没有 hover**，永远半透明；(3) 按钮没有 `white-space:nowrap`。
- **修**：`flex-wrap:wrap` + `gap:4px 12px`；按钮 `flex:0 0 auto;white-space:nowrap`；`@media (hover:none){ .en-acts{opacity:1} }`，同时把 `.toc-tools`（目录行工具）、`.ch-edit`（章名旁按钮）一起提亮。
- **教训**：凡是用 `:hover` 显影的控件，都要配 `@media (hover:none)` 兜底——触屏设备上是真的看不到。多按钮横排必须 `flex-wrap`，否则窄屏必然挤压。

## BUG-2026-020 · 「AI 帮我判断年份」按钮压住下一个字段（v0.9.41 修复）

- **现象**：「收进档案」弹层里「🤖 AI 帮我判断年份」按钮和下面的「在哪儿」标签叠在同一行，文字互相压住（实测按钮 top=272、label top=276）。
- **根因**：`.ml-modal` 里 `<label>` 没设 `display:block`，按钮是 inline-block，后面的 label 被排到同一行。
- **修**：`.ml-modal > button.btn.tiny{display:block;margin:-4px 0 12px}`，让这类紧跟输入框的小按钮独占一行。

## BUG-2026-021 · 导出提示「约 56 MB」，实际文件 78.5 MB（v0.9.41 修复）

- **现象**：整本导出成功，toast 说「152 张图 · 1 段录音 · 约 56 MB」，`Download` 里文件实为 78,512,111 字节。
- **根因**：`packSummary()` 用 `b64.length * 0.75` 估的是**解码后原始字节**（照片+录音本体），而文件里存的是 base64 文本（体积 ≈ 1.33 倍）+ JSON 结构。用户按这个数字判断能否发微信，会误判。
- **修**：`packSummary(pack, bytes)` 接收 `JSON.stringify(pack).length`（b64 全是 ASCII，1 字符 = 1 字节），报出来就是真实文件大小。

## BUG-2026-022 · 正文插图片时相册只能选一张（v0.9.42 修复）

- **现象**：正文段落后面点「＋图 → 照片 → 上传新照片」，拉起的小米相册选择器**只能点一张**，点第二张就把第一张替换掉；一次只能插一张照片。
- **根因**：三层都没开多选，缺一层就回到单选：
  1. `web/app.js` 的 `uploadToEntry()` 建的是 `<input type="file">`，**没有 `multiple`**，而且 `onchange` 只取 `inp.files[0]`；
  2. `MainActivity.onShowFileChooser()` 拉起 `ACTION_GET_CONTENT` 时**没带 `Intent.EXTRA_ALLOW_MULTIPLE`**，WebView 说要多选也没用；
  3. `onActivityResult(REQ_FILE)` 只读 `data.getData()`（单选那一条），多选结果在 `data.getClipData()` 里，即使系统返回多张也只回调一张。
- **修**：
  - 前端 `inp.multiple = true`；`onchange` 把 `files` 全取出来，**一张一张串行**处理（压缩/读盘串行，避免几十张大图同时进内存 OOM），每插一张更新锚点，保持用户勾选的先后顺序；结束按成功数给提示（「放好 3 个」/「放好 2 个，1 个没放进去」），并 `focusEntry(第一张)` 停在原地。
  - Java：`params.getMode() == MODE_OPEN_MULTIPLE` 时 `putExtra(Intent.EXTRA_ALLOW_MULTIPLE, true)`；`onActivityResult` 优先按 `ClipData` 取出全部 URI（`getItemCount()` 逐条），没有再退回 `getData()`。
- **验证**：`tmp/ui_v0942.py`（桌面 Edge 一次 set_files 3 张 → 插 3 条、顺序对、停原地、media 表 3 条）；**小米 9 真机**：相册选择器顶部出现「已选择 N 项」、可连续勾选，点 ✓ 后 WebView 一次收到 4 个 URI，全部插入（sort_key 10.5/11/11.5/12 依次排开，文件名作说明），toast「放好 4 个」。
- **教训**：WebView 的「多选文件」是**三层都要松口**：input 的 `multiple` → `EXTRA_ALLOW_MULTIPLE` → `ClipData` 解析。少任何一层，用户看到的都是"只能选一张"，而且从桌面浏览器上测不出来（浏览器自己实现了多选）。
- 注意：图库页「加照片」仍是单张（每张要填年份/地点/事件三样，多选后要排队填表，另做）。

### 明确没做、以及为什么

1. **按类型预置人生骨架章**：小程序一进来就 6~7 个空章，屏幕小、老人容易迷路，且空章在手机上没有实际内容可看。改为「新建档＝第一章」，让用户自己加章。
2. **Word 导出**：PDF 已经能出（见 FEAT-2026-016），Word 需要 docx 排版引擎，小程序端投入产出不划算；要 Word 用电脑版。
3. **自动云备份**：本小程序是第三方托管，**合法域名白名单配不了**，任何 `wx.request` 到自有服务器都不通；云开发也没开。所以备份方案刻意全部走本地文件 + 微信聊天，不依赖网络。
4. **录音只存不转写（照搬主端 v0.9.37）**：小程序用户多是长辈，纯音频条目看不出内容会更难找；因此保留「能转就转」，但把**原声文件作为必须留底的字段**，转写失败也不丢录音。

### FEAT-2026-016 导出与备份（v0.9.37 内追加）

**问题**：小程序沙盒里的文件出不去，备份只能复制 JSON 文本，图片视频完全带不走；删小程序＝资料全没。

**思路**：微信官方有三条**纯本地**通道，不需要服务器、不需要域名白名单：

| 通道 | API | 平台 | 用途 |
|---|---|---|---|
| 转发到聊天 | `wx.shareFileMessage`（2.16.1+） | 手机 + PC | **主力**：发给「文件传输助手」，电脑微信收下来就落地了 |
| 存到磁盘 | `wx.saveFileToDisk`（2.11.0+） | **仅** Windows / macOS 微信 | PC 上一步到位另存 |
| 打开文档 | `wx.openDocument`（showMenu） | 手机 | 打开 PDF，右上角可转发 / 用其他应用打开 |

**实现**（`utils/exporter.js`，全部纯前端）：

- **ZIP 打包**：手写 store 模式 zip（不压缩 —— 照片视频本来就压过，省一个压缩器）。中文文件名置 UTF-8 标志位（bit 11），电脑解压不乱码。
- **PDF 生成**：离屏 canvas 画 A4（1240×1754 @150dpi），逐页 `canvasToTempFilePath` 出 JPEG，再手写 PDF 的对象表 / 内容流 / xref，每页一张图 `DCTDecode` 直嵌。**中文靠画出来，不用嵌字体**，所以体积小、实现短。
- **单档案**：导出图文 PDF / 导出 zip 备份包（json + `media/` 原文件）/ 复制全文（兜底）。
- **整库**：文字备份 .json（最快）/ 完整备份 .zip（含所有照片视频录音）/ 复制 JSON 文本（老微信兜底）。
- **恢复**：`wx.chooseMessageFile` 从聊天记录选回 .json/.zip → 解 zip → 媒体写回 `USER_DATA_PATH` → 按文件名把 `entry.file` 改写成新设备路径 → `store.importAll()` **合并式**导入（同 id 跳过，不覆盖手机上较新的内容）。

**两个坑（已处理）**：

1. `wx.shareFileMessage` **只允许在点击行为里直接调用**。而生成 PDF 要几秒（异步），异步回调里调用可能失败 → 失败时不报死，把文件留在 `_pending`，弹「文件好了，还差一步 / 现在转发」，用户再点一次就是同步调用，成功率最高。
2. 用户可能重新压缩过备份包 → 解 zip 时只支持 store 方式，遇到 deflate 会统计进 `skippedMedia` 并提示，不假装成功。

**已知限制（诚实说明）**：

- PDF 是**图片型**，文字不能搜索/复制，每页约 150~400KB；一份 30 页的档案大约 5~10MB，微信转发没问题。
- 微信转发单文件有体积限制（经验值 100MB 上下），代码里超 100MB 会给提示建议分章导出。
- 小程序本地文件（照片视频录音）上限约 **200MB**，装满后新照片存不进来 → 设置页显示占用量，≥80% 变红提醒「先备份再清理」。
- 恢复只能从**聊天记录**选文件（`chooseMessageFile` 的固有限制），存在手机文件夹里的选不到。

**验证**：`tmp/exporter-test.js`（字节层 24 项：UTF-8、CRC32、zip 结构、PDF xref 偏移）、`tmp/mp-export-test.js`（导出链路 30 项：mock canvas 出 PDF、手机/PC 两条投递、转发被拒的降级、坏图不出错）、`tmp/mp-restore-test.js`（备份→清空→恢复往返 30 项：路径改写、章节名保留、二次导入不堆叠、坏文件提示）。ZIP 与 PDF 产物另用 Python `zipfile.testzip()` 与手工 xref 解析独立验过。**真机 UI 未验**（等审核通过后做）。
