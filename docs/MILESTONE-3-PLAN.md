# 里程碑 3 · 升级完善优化方案

**版本基线 v0.4.1** ｜ 2026-10-24 ｜ 前置里程碑：v0.4.0（里程碑 2，两端全链路真机打通）

## 〇、这份方案要解决什么

里程碑 1 解决「一个人在一台电脑上把档案做出来」，里程碑 2 解决「换到手机上也能做完，一家人各用各的」。
两者都是**单机 / 单实例**形态：数据在本机，前端握着业务逻辑，服务端只负责把 SQL 和文件转发一下。

新阶段的目标是六件事，但它们不是并列的六件事：

| 你的目标 | 本质要求 | 现在的架构卡在哪 |
| --- | --- | --- |
| 完善功能界面 | 设计系统 + 老年友好 + 离线可用 | 2100 行单文件 `app.js`，样式靠零散 CSS，改一处怕碰坏三处 |
| 扩展使用范围 | 批量导入、家族协作、分享、AI 访谈 | 没有业务 API，没法给第二个客户端复用 |
| 微信小程序 | 一套 HTTPS 业务 API + 原生页面 | **前端直接发 SQL**，小程序端无法安全复用 |
| macOS / Linux | 跨平台宿主 | 已具备（Node 服务 + 静态前端），只缺打包与签名 |
| 前后端微服务 | 清晰的领域边界 | 服务端没有领域层，只有 `/api/query`、`/api/exec` 两个 SQL 转发口 |
| 大型网络平台 | 多租户、可水平扩展、可观测、合规 | 每用户一个 SQLite 文件，横向扩不动；无缓存、无限流、无审计 |

**一句话结论：六件事里有四件被同一个天花板压着——业务语义全在客户端，服务端只是个数据库代理。**
所以顺序不能是「先做小程序 → 再拆微服务」，而是「先把业务语义搬回服务端 → 多端与拆分才有立足点」。

## 一、现状盘点（代码事实，不是印象）

| 项 | 数字 | 说明 |
| --- | --- | --- |
| 服务端 | `server/server.js` 39.5 KB | 认证 5 个接口 + 代理 5 个接口（`query/exec/ai/asr/file`） |
| 前端 | `web/app.js` 100 KB / 2100+ 行，`web/db.js` 45.6 KB | 视图 + 全部业务规则 + SQL 拼装都在这里 |
| 样式 | `web/style.css` 21 KB | 无 token、无组件层 |
| 安卓 | 9 个 Java 文件 3159 行，零第三方依赖，minSdk 21 | 自带 HTTP 服务 + WebView（`LocalServer`） |
| 数据表 | 11 张（+`sessions`） | `archives/chapters/entries/segments/photos/media/shares/settings/ai_profiles/ai_slots/users` |
| 存储形态 | `data/users/<uid>/archive.db` + `files/` | **物理分库**，一万用户 = 一万个 SQLite 文件 |
| 治理 | 197 项自动化测试（8 套） | 这是本阶段最值钱的资产，重构时它是安全网 |
| 产物 | Windows EXE（Node SEA，87 MB）、APK（124 KB 壳 + 资源） | 双击即用，空目录可跑 |

**要继承的三条好设计**（不要在新架构里丢掉）：

1. **物理隔离数据**——用户之间的档案不靠 `WHERE`，靠不同文件/不同 schema。上 PG 后要用 RLS 把这条等价物补齐。
2. **只有系统能力才走 Bridge**——安卓端只把录音、TTS、文件选择下沉原生，其余走 HTTP。这个边界让「同一套前端跑两种宿主」成立，小程序端也照这个思路切。
3. **幂等建表**——`ensureSchema()` 每次打开都跑一遍，任何旧库都能被新版本打开。迁移到 PG 时对应的是**只前进的 migration 链**。

## 二、三个必须先定的地基决策

### 决策 1：业务逻辑下沉，前端不再拼 SQL

现在是：`web/db.js` 直接产出 `INSERT INTO entries ...`，服务端 `apiExec` 原样执行。
这条路在单机版成立（库就在本机、用户就是主人），但在**联网版是三个致命问题**：

- 小程序端把 SQL 暴露在网络请求里 → 任何抓包的人都能构造任意 SQL；
- 无法在服务端做「谁可以读哪本档案」的判断，只能靠客户端自觉；
- 服务端拿不到业务语义 → 没法缓存、没法审计、没法限流、没法做灰度。

**做法（不是一次性重写，是分层切换）**：

```
现在:   app.js ──SQL──> /api/exec ──> SQLite
目标:   app.js ──JSON──> /api/v1/* ──> domain/* ──> repo/* ──> SQLite | PostgreSQL
                add.js ─┘                     （同一份领域代码，两种存储驱动）
```

- 新增 `server/domain/`（archives、chapters、entries、segments、media、ai、share 七个模块），每个模块只暴露语义化函数：`createArchive()`、`appendSegment()`、`transcribeSegment()`；
- 新增 `server/repo/`（仓储接口 + `sqlite/`、`pg/` 两套实现），领域层不认识 SQL 方言；
- 前端 `db.js` 保留**方法签名不变**，内部从「拼 SQL」改成「调 API」。这样 2100 行界面代码一行不用改——这是能在两周内完成切换的关键；
- `/api/query`、`/api/exec` 只在 `MYLIFE_MODE=local` 下开放，联网部署时直接不挂载。

**验收**：`web/db.js` 里不再出现 `INSERT/UPDATE/DELETE` 字面量；197 项旧测试全绿；新增 API 契约测试 ≥ 40 项。

### 决策 2：存储双驱动，但不追求「一套 SQL 跑两边」

- 单机版（EXE / APK / 本机网页）继续 SQLite，**离线可用是产品差异点，不能砍**；
- 平台版用 PostgreSQL 16：主键改 `bigint generated always as identity`，时间字段统一 `timestamptz`，`facts_json` / `config_json` 走 `jsonb`；
- 差异收敛在 `repo/pg` 里，领域层只写「取这本档案的全部章节及其条目」这种话；
- 迁移工具：`server/migrations/pg/001_init.sql` 起，只前进、可重放、每条带 `IF NOT EXISTS`；
- 数据搬迁给一条命令：`node tools/migrate-to-pg.js --user 1`（读 SQLite → 写 PG → 校验行数与校验和）。

**已知的坑**（提前写进方案，省一轮返工）：SQLite 的 `INTEGER` 主键在 PG 里不会自增；`datetime('now')` 要换成 `now()`；`LIKE` 大小写在 PG 下敏感；原来的 JSON1 依赖已在 v0.4.1 移除，算是省了一劫。

### 决策 3：前端两条线，不要强行统一

| 线 | 用途 | 技术 | 为什么 |
| --- | --- | --- | --- |
| `web/`（存量） | 安卓 WebView、Windows EXE、老浏览器 | 保持 ES5 单文件 | 安卓 5/6 的内核老，动它就是拿里程碑 2 的成果冒险 |
| `web-next/`（新增） | 平台版、桌面版、PWA、分享页 | TypeScript + Vite + 轻组件层 | 需要设计系统、需要按需加载、需要离线缓存，ES5 撑不住 |

两条线**共用** `style.css` 的设计 token 和同一套 API 契约。`web-next` 不是重写业务，是把视图层搬过去——逻辑已经在决策 1 里搬到服务端了，前端只剩「取数据、画界面」。

### M3.3 · macOS / Linux（v0.7.0）｜2 周

现成资产：Node 服务 + 静态前端，理论上换个平台的 Node 就能跑。缺的是**分发形态**。

| 路线 | 体积 | 工作量 | 取舍 |
| --- | --- | --- | --- |
| A. Node SEA + 系统默认浏览器 | 80–90 MB | 1 天/平台 | 最省，但「像网页」——没有独立窗口与图标 |
| B. Tauri 2 壳（内嵌 WebView，复用本机 HTTP 服务） | 8–15 MB | 3–5 天/平台 | 真窗口、体积小；需要 Rust 工具链，Linux 依赖 WebKitGTK |
| C. Electron | 150 MB+ | 2 天/平台 | 成熟但重，与「老人电脑」的磁盘现实不匹配 |

**推荐 A → B 两步走**：先 A 出可运行的 mac/linux 包（一周内能验证服务端跨平台没问题），再套 B 的窗口。Linux 侧 Tauri 依赖多，改用 `WebKitGTK + 自绘窗口` 的成本可能高于收益，**A 方案对 Linux 反而是最优解**。

**必须提前算进去的坑**：

- macOS 未签名应用会被 Gatekeeper 拦（「已损坏」提示）→ 要么买 Apple 开发者账号（99 美元/年）做签名 + notarization，要么在文档里教用户右键打开 / `xattr -d`；
- Linux 用 `AppImage` 最省事（免安装、免 root），再补 `.deb`；
- 文件路径大小写敏感、`/` 与 `\` 的差异：`server.js` 里所有 `path.join` 都要过一遍，`files/` 的相对路径不能有反斜杠字面量。

**验收**：Ubuntu 22.04 与 macOS 14（Intel/Apple Silicon 各一）双击可跑，录音、转写、朗读、导出四项通过。

### M3.4 · 微信小程序（v0.7.x）｜4 周

**先说清限制**（这些决定方案形态，不是可选项）：

| 限制 | 影响 | 对策 |
| --- | --- | --- |
| 必须 HTTPS + 已备案域名，且域名加入小程序后台白名单 | 不能连本机/内网 | 平台版必须先上线（M3.5 的一部分要提前） |
| 个人主体不能做「内容社区」，工具类可过 | 类目选「工具-效率」或「教育-在线教育」 | 首版只做「个人档案管理 + 家人共享」，不做公开广场 |
| `web-view` 只能打开业务域名页面，且不能承载核心交互 | 不能把现有前端整包塞进去 | 主体用原生页面，`web-view` 只用于「精装预览/分享页」 |
| 录音是 `RecorderManager`，输出 mp3/aac，不是 WAV | 现有 ASR 链路按 WAV 设计 | 服务端加 ffmpeg 转码（已有转码需求的伏笔） |
| 无 DOM、无 `localStorage` | 前端不能复用 | 只复用 API 契约与设计 token |
| 审核要求《隐私政策》+ 用户隐私保护指引 | 涉及手机号、录音、照片 | 提前准备文案与授权弹窗 |

**做法**：

- 新建 `miniprogram/`：`pages/home|archive|collect|settings`，WXML + 轻量状态管理（不引第三方框架，减少审核变量）；
- 登录：`wx.login` → 服务端 `code2session` → 绑定手机号（`getPhoneNumber`）→ 复用现有 `sessions`；
- 录音：`RecorderManager` 16k 单声道 → 上传 `/api/v1/segments`（multipart）→ 服务端 ffmpeg 转 WAV → 走现有 ASR；
- 朗读：微信同声传译插件（`WechatSI`）或服务端 TTS 出 mp3；
- 分包：主包 ≤ 2 MB，图片与字体走 CDN；
- 分享：`onShareAppMessage` + 分享页 `s/:slug`，落地页用 H5，链路闭环。

**验收**：真机（iOS + Android 各一）完成「登录 → 建档案 → 录音 → 转文字 → 生成 → 朗读」；审核一次通过；冷启动 < 2s。

### M3.5 · 微服务与云平台（v0.8.0 → v0.9.0）｜6 周

**先纠一个常见误区**：以现在的体量直接上「十几个微服务 + K8s + 服务网格」，得到的是运维复杂度，不是扩展性。正确顺序是**模块化单体 → 按压力拆三个**。

#### 第 1 步：模块化单体（v0.8.0，2 周）

单进程部署，但代码边界硬隔离（每个 domain 模块只能通过 `repo` 与事件总线交互，禁止跨模块直连表）。
部署形态：`docker compose up` —— `app` + `postgres` + `redis` + `minio` + `caddy`。

#### 第 2 步：按真实压力拆（v0.8.x，2 周）

只拆这三个，其余留在主应用里：

| 服务 | 为什么拆它 | 技术 |
| --- | --- | --- |
| `media-worker` | 转码、长音频切段、PDF 生成、EXIF 抽取都是 CPU/IO 重活，会把 API 拖死 | 独立进程 + BullMQ（Redis）队列，可多副本 |
| `ai-gateway` | 模型调用要统一配额、重试、降级、成本核算、审计 | 独立服务，主应用只发「转写这段音频」 |
| `share-renderer` | 公开页要被微信/搜索引擎抓，需要 SSR 与 CDN 缓存，与登录态解耦 | 独立服务 + CDN，可独立扩容 |

**不拆**：`auth`（拆了要处理分布式会话，收益为零）、`archives`（域内事务强，拆了就要上 Saga）。

#### 第 3 步：平台化基础设施（v0.9.0，2 周）

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 数据库 | PostgreSQL 16（托管） | 每用户一库改「单库多租户 + RLS」，`app.uid` 会话变量做行级隔离 |
| 缓存 | Redis 7 | 会话、限流（滑动窗口）、热点档案、分享页 HTML |
| 文件 | S3 兼容（MinIO 自建 / COS、OSS 托管） | 存储抽象 `Storage` 接口，单机走本地盘，平台走对象存储 |
| 队列 | BullMQ | 长任务、重试、延迟任务、进度回传（ASR 进度条有了） |
| 网关 | Caddy / Nginx | TLS 自动续期、压缩、限流、静态缓存 |
| 可观测 | OpenTelemetry → Prometheus + Grafana + Loki | 三条命脉指标：API p95、ASR 队列积压、失败率 |
| CI/CD | GitHub Actions / Gitee Go | 单测 → 构建 EXE/APK/镜像 → 打 tag → 发布 |
| 灾备 | 每日全量 + WAL 归档，异地保留 30 天 | 人生档案丢不起，恢复演练每季度一次 |

**验收**：单台 2C4G 支撑 500 并发读、50 并发写，API p95 < 200ms；ASR 队列积压 < 30 秒；杀进程后数据零丢失（WAL 回放验证）。

### M3.6 · 平台化（v1.0.0）｜4 周

- **多租户 / 机构版**：养老机构、地方档案馆、家族理事会——一个机构下多本档案，管理员看板、批量导出；
- **开放 API**：`/api/v1` 已经存在，补 API Key、配额、Webhook（新档案/新章节通知）；
- **数据权利**：一键导出全量（JSON + 原始媒体 zip）、一键注销与彻底删除（30 天冷静期）；
- **合规**：个人信息保护法「单独同意 + 最小必要 + 可携带」三件套；等保二级测评的前置自查清单；
- **运营**：埋点（隐私友好、不采集档案内容）、崩溃上报、版本公告页。

**验收**：一份《隐私政策》《用户协议》《数据处理附录》可对外；删除请求 30 天内完成且留痕；机构版能导入导出 100 本档案。

## 四、技术选型对照（含否决理由）

| 议题 | 候选 | 结论 | 理由 |
| --- | --- | --- | --- |
| 后端框架 | 继续用 `http` 模块 / Fastify / NestJS | **继续 `http` + 自建路由表** | 现有 39 KB 服务端够用，迁移成本 > 收益；NestJS 的装饰器与 DI 对这个体量是负担 |
| ORM | Prisma / Drizzle / 手写 SQL | **手写 SQL + 薄 repository** | 现有 SQL 已成熟；ORM 在 JSON 字段与 RLS 上会漏抽象 |
| 前端框架 | 保持原生 / Vue / React | **`web-next` 用 Vue 3 + Vite** | 模板语法贴近现有字符串拼接的心智；React 的生态优势在 C 端重交互场景，这里用不上 |
| 小程序 | 原生 / Taro / uni-app | **原生** | 依赖少、审核变量少、包体可控；跨端框架省的那点代码抵不上调试成本 |
| 桌面 | Node SEA / Tauri / Electron | **SEA 先行，Tauri 兜底** | 见 M3.3 |
| 数据库 | SQLite / PG / MySQL | **SQLite（单机）+ PG（平台）** | 单机离线是差异点；PG 的 RLS、`jsonb`、`tsvector` 正好对应多租户与检索 |
| 编排 | Docker Compose / K8s / Serverless | **Compose 起步，K8s 到 10 台再上** | 单机 K8s 只会增加故障面 |
| 队列 | BullMQ / NATS / RabbitMQ | **BullMQ** | Redis 反正要装，少一个中间件 |

## 八、明确不做（控制范围）

- ❌ 实时多人协同编辑（Operational Transform 的成本远超收益，家族协作用「分章分工 + 冲突提示」就够）
- ❌ iOS 原生 App（先用小程序 + PWA 覆盖，App Store 审核与年费在这个阶段不划算）
- ❌ 自建 ASR/LLM 模型（继续走供应商，`ai-gateway` 做多路降级）
- ❌ 区块链存证（伪需求，公证与时间戳按需对接第三方即可）
- ❌ 视频剪辑（只做播放与归章）
- ❌ 服务网格 / 事件溯源 / CQRS（这个体量上去就是负债）

## 九、里程碑 3 完成定义（DoD）

全部满足才算收官：

1. 六个端跑同一套业务 API：Windows / macOS / Linux / Android / 网页 / 微信小程序；
2. `web/db.js` 零 SQL 字面量，`/api/query|exec` 仅本机模式存在；
3. 197 项旧测试 + 新契约/无障碍/双库对比测试全绿，总数 ≥ 300；
4. 平台版在云上稳定运行 30 天，可用性 ≥ 99.5%，有备份与恢复演练记录；
5. 一本 100 章、500 条目、300 张照片的真实档案，在小程序与桌面端都能流畅打开（首屏 < 2s）；
6. 三份合规文档可对外，删除与导出权利可自助完成；
7. `docs/` 里的架构图、API 文档、部署手册与代码一致（不是过期文档）。
